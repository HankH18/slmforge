## 4. How to read this table

`spec_pass` is `every programmatic checker passes` **and** `judge task-quality is
at least the pinned threshold`. Constraint pass/fail is entirely programmatic —
`constraints/checkers.py`, no model call, no network. The judge scores task
quality only and can never overturn a checker; it exists to block the degenerate
strategy of satisfying every constraint with empty or off-task text.

`spec_adherence` is the mean of `spec_pass` over scored rows. `robustness` is the
same quantity restricted to the adversarial subset, where the task's own subject
matter pulls toward the banned token and an embedded nudge argues the rules are
optional.

**This table is not the finding, and reading it alone will mislead you.** The
headline metric is a cliff: it requires zero violations, so it cannot distinguish
a response that breaks a constraint once from one that breaks it forty times, and
it reports no change across two data iterations that a paired test on the same
scenarios separates decisively. It is also an average over two halves of the eval
set that move in opposite directions — trained constraint families improve,
untrained ones degrade, and the aggregate is their sum.

Both effects are quantified, with the statistics and the per-split decomposition,
in [`BRAINLIFT.md`](BRAINLIFT.md) and [`EFFICIENCY_CURVE.md`](EFFICIENCY_CURVE.md).
Those numbers are re-derived by `scripts/curve_report.py` and
`scripts/compare_checkpoints.py`, which read the same committed transcripts.

## 5. The staff held-out eval set

The harness takes any scenario file:

```bash
python eval.py --model hf:HankH18/qwen3-1.7b-forbidden-constraint-holder@c19712a72932b503f28fe063d1962acc9e8c3fb8 --eval-set <path-to-staff-set.jsonl> --constraints <path-to-their-constraints.jsonl> --out <your-run-dir>
```

**Check the file first — it costs nothing and it can save the whole run:**

```bash
python scripts/preflight_evalset.py <path-to-staff-set.jsonl> [their-constraints.jsonl]
```

Preflight renders every row, resolves every constraint id, runs every referenced
constraint through the pinned checker, and reports what the set contains. It
exists because of a defect this project found while preparing for exactly this
scenario: `pressure`, `split` and `k` were read only inside the aggregation step,
which runs *after* every generation and every judge call, so a supplied file
missing any one of them destroyed a finished run and wrote nothing to disk.
`eval.py` now validates the set before it generates a single token and exits
non-zero, and `harness.validate_eval_set` reports every problem in the file
rather than the first.

Two limits are worth stating plainly rather than discovering mid-run:

* **Constraint ids are pattern-pinned**, and each constraint's family and split
  must match this project's registry. A staff constraint library using its own id
  scheme is refused by the checker, not silently mis-scored. Preflight catches
  this for free; the fix is to map their ids onto the registry's scheme before
  running, and the mapping should be published alongside the numbers.
* **Only the registered constraint types can be checked.** There is no extension
  point. A supplied set introducing a constraint type this project does not
  implement is not gradeable by this harness, and that has to be disclosed rather
  than worked around by scoring the subset that happens to fit.

The local proxy for a held-out set is already in the eval set and is reported in
the generated block's split breakdown: constraint families that appear in **zero**
training rows, so the split measures transfer to constraint types the model never
saw. That proxy is where this project's least flattering result lives.
